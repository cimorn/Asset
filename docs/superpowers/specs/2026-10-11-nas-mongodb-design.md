# 资产罗盘迁移到 NAS MongoDB

## 已确认的目标

用户已明确：飞书不再使用，MongoDB 是网站的正式账本。保留现有资产页面、分类、计算规则、更新弹窗和图表。编辑先保存在浏览器草稿，点击“上传”后才保存正式账本。

本次只改 `资产罗盘/website`。桌面 EXE 暂不迁移；迁移后的桌面版仍连接旧飞书账本，不能继续与新版网站同步，需要以后另行改造。

## 推荐部署

- 现有 NAS 的 `mongodb` 容器继续使用 MongoDB 7.0，不重装、不搬动其磁盘目录。
- 在该实例中新建 `assetmanager` 数据库和独立的 `assetmanager_app` 账号，仅授予该库的 `readWrite` 权限。
- 新建资产罗盘 Node 22 容器，同时提供现有 Vite 页面和 API。加入 MongoDB 所在的 Docker 内部网络。
- `asset.mcj.life` 通过现有 Cloudflare Tunnel 指向新容器，页面、登录和 API 保持同一域名。迁移前验证可用的独立临时入口，再切换正式域名。
- 现有博客、密码库及其隧道路由不变。MongoDB 不向公网开放端口。资产运行容器不保留 Mongo 管理员凭据或飞书密钥。

这会更换网页的运行位置，但不会重新设计前端。前端只调整“飞书”相关提示和数据来源状态，让“上传”“读取”明确指向 NAS。

另一个可行方案是保留 Render 提供页面，再转发 API 到 NAS。它需要额外维护代理、鉴权和故障处理。本次推荐直接在 NAS 提供现有页面与 API，减少一个依赖。

## 数据结构与计算

正式数据使用版本化账本，避免把资产、市值、收益等多个汇总表独立写入后产生不一致。

| 集合 | 保存内容 |
| --- | --- |
| `ledgers` | 当前账本编号、已发布版本号、内容摘要、上传时间、短期上传请求回执 |
| `ledger_versions` | 不可变的版本内容：流水输入、各日期汇率、资产辅助信息、用户设置及迁移来源说明 |

版本内容延用现有 `ledgerInputs` 的含义，排除可以重新计算的投资收益、账户汇总和曲线点。读取版本后通过现有 `projectLedger` 重算返回前端；分类和代码来自用户的流水，图标、备注等资产辅助信息保留。

- 流水保留稳定 ID、资产关联、操作、日期、同日顺序、金额及更新后的总余额。
- “剩余”和“更新市值”保留现有替换余额的规则，不把新余额当作追加投入。
- 各日期的汇率分别保存，保持数值精度及四位小数显示，按变动日期选择生效汇率。
- 不把汇率更新当作资产买入，不重复累加余额或收益。

## 上传与并发

`打开网站 → 读取 MongoDB 正式版本 → 编辑到浏览器草稿 → 上传 → 核对并保存新版本 → 重新读取确认`

接口保留现有两阶段上传方式及浏览器中断恢复，逐步将内部接口名从飞书改为通用账本接口。

1. 服务端验证输入，使用浏览器编辑前的版本、草稿及数据库最新版本合并互不冲突的流水和汇率。
2. 同一个字段被两台设备同时改动时返回明确冲突，不静默覆盖；浏览器草稿保留。
3. 完整新版本先写入 `ledger_versions`。之后以当前版本号为条件，原子更新 `ledgers` 的版本指针和上传回执。竞争失败时重新读取、合并、重试，不能发布一半内容。
4. 请求 ID 随发布一起保存；网络中断后同一请求再次上传不会重复生成流水。
5. 读取只使用已经发布的完整版本。数据库错误不替换成空账本，不清除浏览器草稿，返回可见错误。

这种发布方式适用于当前没有配置副本集的 MongoDB，不要求为了跨集合事务重建数据库。单条指针文档的条件更新依据 [MongoDB 单文档原子性说明](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)。

## 迁移与切换

1. 读取飞书的当前完整账本，生成带日期和 SHA-256 摘要的私密迁移备份；整个过程只读，不修改飞书。
2. 在正式切换前停止旧网站的新上传，并重新读取最终账本。需要先处理当前浏览器未上传草稿；不能直接清空本站存储。
3. 迁移工具检查目标为空、备份结构正确、分类与历史汇率完整，然后导入首个正式版本。已存在账本时拒绝覆盖。
4. 回读 MongoDB，核对资产与流水 ID、数量、历史汇率、分类金额、总资产、成本及收益。现有资产计算必须保持一致。
5. 验证新网站登录、草稿恢复、真实数据库上传及另一浏览器读取，测试写入使用独立验证账本。
6. 验证通过后切换 `asset.mcj.life`。旧 Render 和飞书账本保留作为迁移前副本，旧站保持停止写入。

如果切换失败，先确认 NAS 是否已有新上传。旧飞书不包含切换后的新内容，不能直接回退而丢失新记录。

## 配置、备份和运维

NAS 项目文件建议放在 `共享文件夹/docker/assetmanager/`，包含源码、Compose 配置、独立私密 `.env` 和备份目录。MongoDB 实际磁盘文件继续由现有实例管理，不手动复制或拆分数据库文件。

运行配置包含 `APP_PASSWORD`、`SESSION_SECRET`、`APP_ORIGIN` 和资产库连接配置。尽量保留当前网站的登录设置；会话签名密钥和上传恢复记录要配套处理，不随意重置。Mongo 密码和迁移备份不进入 Git、安装包或前端资源。

设置中的完整账本下载功能继续保留；另外提供服务端完整导出及向空库恢复的维护命令，导出覆盖正式账本、历史版本、上传回执和结构版本。至少在 NAS 之外保存一份备份，恢复工具默认预检查并校验摘要。

NAS 和办公室网络离线时，当前浏览器可显示已有缓存并继续编辑草稿；上传明确失败，恢复连接后再上传。

## 验收

- 原有分类、各日期汇率、剩余余额、资产成本和收益核对一致。
- 缓存编辑不修改正式账本；点击上传才持久保存。
- 重启资产容器、重开网页后仍可读取正式数据。
- 两台设备的不同流水均保留；重复上传无重复记录；真正冲突不静默覆盖。
- 初次读取失败不显示成功、不以空账本覆盖已有缓存。
- 未登录不能读写账本，数据库凭据只留在后端。
- 资产账号不能访问 `website` 数据库，现有博客及密码库保持可用。
- 正式域名实际读取 NAS 数据后才能声明迁移完成。
